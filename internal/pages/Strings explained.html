Strings explained

On string storage and operations.
Last modified 23/04/2026

Context: yesterday I saw a post on X saying that strings are “slow”, and provided some reasons for why that would be. Leaving aside the fact that those stated “facts” are wrong, I think knowing how things work is much better than memorizing some trivia that you will most likely forget in the future.

Variables and storage

Every piece of data takes up some space in memory.

Many programming languages use types Types are used for other things too, but that is another story. to define the amount of memory that a piece of data will take up. For example, in C and C++, one might say that they want a variable of type int and, on most computers, compilers will generate code to reserve 4 bytes of space for that variable. You can easily get this information through the sizeof operator.

C 
int a = 0x42;

If you want to be sure that the size is what you expect and the compiler supports it, you can include the <stdint.h> header and use int32_t. This way you explicitly say that you want the variable to be 32 bits (4 bytes) in size.

C 
int32_t a = 0x42;

Of course this puts a limit to how many possible numbers can be represented by that variable. 32 bits of storage means 232 (or 4’294’967’295) combinations of bits: the range of values that we can represent in a 32-bit variable is [0, 4’294’967’295], or [-2’147’483’648, 2’147’483’647] if we choose to reserve half of it for the negatives.

For a beginner this may sound like a problem: what if I need a bigger range? Then, with practice and experience, you learn to worry about problems you have instead of the ones you might have. Depending on the domain of the problems you’re solving, you could even realize that you almost never need anything outside that range and, for the few cases where you do, there are solutions you can implement.

The compiler and the stack

What is the advantage of knowing the size of variables ahead of time? It’s so that the compiler can generate extremely efficient code.

For starters, allocation (reserving the memory necessary to hold the variables) and deallocation (releasing the memory so that it can be reused later) can be reduced down to one instruction each. Imagine a big, invisible array of bytes living inside your program, called the stack; there’s also an index into this array, called the stack pointer. The stack is where all your local variables are stored. The stack pointer keeps track of which elements of the stack are considered “free”, so that new variables won’t overwrite the ones that already exist.

For each function, the compiler computes the total sum of the sizes of all the local variables it has. Then, when generating the function’s code, it starts with an instruction that increments the stack pointer by that amount. At the end of the function, another instruction moves the stack pointer back to where it was.

This is why some C compilers (and all C++ compilers!) don’t allow you to use a variable as the length of an array: you would make it impossible for it to predict the size of the allocation.

The complexity of strings

The reason that it makes sense to store numbers in fixed-size variables is because it is possible to define the concept of a range. Every value inside that range will get a dedicated combination of the N available bits for that variable size. As the program does operations on a numeric variable, only the value stored in the variable changes, not its size.

Strings are complicated. You can’t define a range of strings in a way that makes sense for all applications. They necessarily have to be represented as an ordered collection of smaller elements. As the program operates on them, these collections will have to vary in size.

Usually, though, strings are stored somewhere else. Your variables do not contain the string contents, but only a pointer to it; the memory address of the character array. When you move your variables around, you don't always copy the entire string contents: you can also choose to only copy the pointer, which will be much smaller most of the time.

C 
char *the_story_so_far = "In the beginning, the universe was created.";

Where are they stored, if not on the stack? It depends. Some languages choose that for you; other languages let you control it.

In C (and probabily many other languages) string literals are placed in a read-only section of the executable. That is, if you try to modify their contents you'll likely crash. Attempting to modify the contents of a string literal is technically undefined behaviour in C and C++. Either way, bad things will happen.

C 
char *the_story_so_far = "In the beginning, the universe was created.";
the_story_so_far[0] = 'i'; // This line will probabily crash

Strings are just bytes, though, just like anything else. You can point to any place in memory and call that a string.

C 
char *str = 0x42FD5601;

Ok, maybe not like that.

C 
char *str = malloc(sizeof(char) * 20);

That's better.

If you're using C++ you can use a std::string; its constructor will dynamically allocate the right amount of memory and copy over the string contents.

In short, a string is not tied to a particular type of storage. Strings are a convention.

Storing the length

Since we established that every string has potentially a different length, we need a way to store for each string what that length is.

C and C++ inherited their convention from assembly programmers: define a special value that goes at the end of the array and indicates termination. We use the null character ('\0', or simply 0) as this special value, and we call a string that uses this convention a null-terminated string.

C 
char *msg = "Hello";

At the time C was designed, this brought great advantages.

The first advantage is that it only uses 1 extra byte per string, no matter its length. Another one is that you don't need to pass an extra argument to functions, which costs instructions.

Building a string

A common string operation is concatenation. It's what turns the strings "night" and "mare" into "nightmare".

The most obvious way to concatenate "night" and "mare" is the following:

  1. Find the length of "night" (5)
  2. Find the length of "mare" (4)
  3. Compute the length of the new string (5 + 4 = 9)
  4. Allocate memory for the new string
  5. Copy the contents of "night" into the first part of the new string
  6. Copy the contents of "mare" into the second part of the new string

In code:

The most obvious way to concatenate three strings is to just do it associatively: concatenate the first two, then concatenate the result with the third.

concat(A, B, C) == concat(concat(A, B), C)

This works. However, it's doing an extra allocation (the temporary result of A + B) and two extra copies (copy both A and B into the temporary result). The allocation may or may not matter, depending on your allocation strategy. The extra copies do matter, and they add up really quickly

String war crimes

In light of these discoveries, I'd like to look at some string war crimes.

I just need the length

C++ 
void example(void) {
	std::string str = "A really, really long string that contains many characters";
	std::cout << "length = " << str.length() << std::endl;
}

Somebody said they saw code like this in production. I've definitely written code like this when I was in high school and didn't know what I was doing.

If you paid attention so far, it shouldn't take long to see why this is bad. It's taking a string literal, stored in read-only memory and null-terminated; it's scanning it all the way to the end to find the null terminator and determine its length; it's allocating space for a copy, then copying it into a std::string object. All that just to call the length method, to get the length again, then destroy the string as it goes out of scope.

If you just want the length of a string literal, use sizeof:

C++ 
void example(void) {
	size_t str_length = sizeof("A really, really long string that "
							   "contains many characters") / sizeof(char);
	std::cout << "length = " << str_length << std::endl;
}

Case-insensitive comparison

C++ 
bool compare_insensitive(std::string a, std::string b) {
	return std::tolower(a) == std::tolower(b);
}

Other languages

You may be using a language that doesn't allow you to control string operations like C/C++. However, even when you can't control the memory directly, knowing these things is still useful to identify possible performance problems.

To be aware that there is a problem is better than not, and having an idea about what the problem is is better than not having any idea.
