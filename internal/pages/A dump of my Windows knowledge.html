A dump of my Windows knowledge

Things I learned over the years about programming on Windows
Last modified 5/04/2026

The Windows Operating System has a long history. It has tons of features, many of which are hidden, deprecated, undocumented, or simply explained really poorly. This page is an attempt to collect all the things I've found out about the Windows programming interface through documentation, articles, videos, live streams, experimentation, open source code, conversations on Reddit, Stack Overflow and Discord.

Yes, Windows programmers are pushing the system towards its demise. But I don't think it'll be abandoned shortly, as some programs only exist on Windows and some companies are forcing all their employees to stay. Oh, and video games exist.

As of now, it is far from complete. I will update it as I have time to write, or as I find out new things.

Exploring MSDN

Microsoft has the extremely good habit of localizing all of its software to many languages. It also has the extremely bad habit of letting some of these translations be done by automatic tools, or recently even AI. Not only this is extremely noticeable and distracting as some of the sentences are obviously wrong; for technical information, such as compiler error messages and API documentation, it's also useless at best and confusing at worst, because some of the terminology only exists in english and trying to forcefully translate it to other languages is impossible.

MSDN, the website for Microsoft documentation (and other things), is one of those auto-translated things.

Thankfully some very kind people have thought about this, and made a Chrome and Firefox extension called “FFS MSDN in English” that automatically redirects every non-english version of MSDN pages to their corresponding english version.

The Windows SDK headers

A lot of the functionality that Windows offers is exposed in the glorious windows.h header. It is actually a collection of other headers, and macros that control how these other headers are included.
For example, the UNICODE macro controls how some of the older string-related structs and functions are declared.

Because it contains so much stuff, to avoid polluting the global namespace and increasing compile times, some macros exist to exclude some of the declarations from the header. If you only want to use the most common stuff, define the WIN32_LEAN_AND_MEAN macro, like this:

C 
#define WIN32_LEAN_AND_MEAN
#include <windows.h>

Window creation

A window, the thing that Windows was named after, is rather weird to create. If you've never done it before, it will seem difficult, as there are many pieces that you need to connect. After a couple of times you'll change your mind, and think it's not so bad anymore. Then you'll change your mind again, realizing that you're experiencing weird behaviours that you don't want, and that in order to fix those you'll have to bend over backwards. Don't worry, not even official Microsoft programs get it right; not even the code samples that they give you in order to learn Windows. That's how bad it gets.

The mere act of creating a Window isn't too difficult: just call the CreateWindow function (or rather, macro). But that won't get you anywhere; you need to understand the bigger picture:
If you create a window with CreateWindow, you then need code that tells the compute what to do after the window was created: what to draw on it, what happens if the user interacts with it, and so on. Graphical programs are traditionally written using a loop: first the code checks if the user has done something, picks the appropriate response and communicates it to the user, then repeat forever (or until the user exits the program). This is usually called an event loop or a message loop. Imagine that your program will look something like this:

begin:
	create window

	until the user quits:
		wait for a user interaction
		process that interaction
begin:
	create window

	until the user quits:
		wait for a user interaction
		call the event handler

in the event handler:
	process the interaction

The window class

In Windows, each window has a class. In this case, the word "class" has nothing to do with the C++ construct. It is simply a way to group functionality between similar windows. You need to create a window class, even if you intend to only have 1 window of that class.
To create a class, declare an instance of the WNDCLASS structure, fill in the members, then call RegisterClass:

C 
WNDCLASS WindowClass;
/* Initialize */

RegisterClass(&WindowClass);

Note: the window class is one of those things that have a different definition depending on the UNICODE macro. The structure is defined to be either WNDCLASSA or WNDCLASSW, and the RegisterClass is a macro that expands to either a A or a W. We will see why this matters shortly; for now, let's just switch our code to use the W version.

The WNDCLASS* structures have a lot of fields, but don't worry: you only have to set 3 of them to have a valid class; the others can be set to 0, and they will take default values.

The first field to set is lpszClassName (long pointer to string zero-terminated ClassName). It is the name that the system will register the class with. It needs to be unique for the entire process, and it is case-insensitive ("myclass", "MyClass" and "myClass" are equivalent). You also need to be aware of some system-defined names that are already registered at the start of your process, that are used for buttons and similar controls.

C 
WindowClass.lpszClassName = L"Main Window Class";

The second field is lpfnWndProc (long pointer to function Window Procedure). It's a pointer to the function that will process the events from our event loop. Windows provides a default one, DefWindowProc (also coming in narrow and wide variants). Let's use that for now.

C 
WindowClass.lpfnWndProc = DefWindowProcW;

The last essential field of our class is hInstance (this one is easier: handle to an Instance). It's an opaque handle to the instance of the current module (executable or dll). It's the first parameter of the WinMain family of entry points, or, if you're going with a traditional main, you can get it like this:

C 
WindowClass.hInstance = GetModuleHandleW(NULL);

So now, just bulk-initialize everything else to zero and you'll have a valid window class.

C 
WNDCLASSW WindowClass = {0}; // Set everything to zero
WindowClass.lpfnWndProc   = DefWindowProcW;
WindowClass.hInstance     = GetModuleHandleW(NULL);
WindowClass.lpszClassName = L"Main Window Class";

RegisterClassW(&WindowClass);

The window

Now that the window class is registered, it's time to call CreateWindowW. It has quite a few parameters. The most important are:

  • lpClassName – The name of the class that this window will belong to;
  • lpWindowName – The name of the window itself. The way this'll be used depends on how the window is displayed. For windows with a title bar, it'll be the title of the window;
  • dwStyle – The “style” of the window, or its graphical properties;
  • x, y, nWidth, nHeight – The initial position and size of the window;
  • hInstance – The handle to the process’ module

Here's an example of how you might call it:

C 
RegisterClassW(&WindowClass);

HWND Window = CreateWindowW(
	WindowClass.lpszClassName,	// The class name
	L"Hello Windows",			// Title of the window
	WS_OVERLAPPEDWINDOW,		// The "style" of the window
	CW_USEDEFAULT,				// Left edge
	CW_USEDEFAULT,				// Top edge
	CW_USEDEFAULT,				// Width
	CW_USEDEFAULT,				// Height
	NULL,						// Parent window	(optional)
	WindowClass.hInstance,		// Module handle
	NULL,						// Menu				(optional)
	NULL						// Additional data	(optional)
);

CreateWindow* returns a handle to the window that was created, or NULL if it fails.

If you compile and run your program now, you will see... nothing. Windows are invisible unless otherwise specified. The next step is to make the window visible.

Showing the window

A window's visibility is part of its style. You can create a window so that it's immediately visible, or you can make it visible later.
To make it visible from the start, modify the call to CreateWindowW so that it uses the WS_VISIBLE style. Since window styles are bit-flags, to combine styles is as simple as using a bitwise-or:

C 
	WS_OVERLAPPEDWINDOW|WS_VISIBLE,

To make it invisible later, call the ShowWindow function whenever you're ready:

C 
HWND Window = CreateWindowW(...);
/* Anything you want here */

ShowWindow(Window, SW_SHOW);

More about visibility later. Now, if you compile and run the code, a window will briefly appear on the screen and then immediately disappear. This is expected: the program ends, and the Operating System destroys all the windows it created.

The message loop

When a thread creates a window, it also implicitly creates a message queue. The system pushes messages on this queue:

  • When the user interacts with the window, such as when they click on it with the mouse;
  • When something happens in the system that a program might care about, such as when the monitor resolution changes.

Each message has a numeric constant, and a macro in the windows headers that expands to that constant. For the two messages mentioned, they are WM_LBUTTONDOWN and WM_DISPLAYCHANGE.

The GetMessage* functions remove the first message from the thread's queue, then fill a MSG structure with information about it.

C 
MSG Message;
GetMessageW(&Message, NULL, 0, 0);
C 
MSG Message;
while (GetMessageW(&Message, NULL, 0, 0) > 0) {
	TranslateMessage(&Message);
	DispatchMessageW(&Message);
}

The window procedure

When you call DispatchMessage the system will use the message struct to figure out what the target window of that message is. It will then lookup the window's class, and from that call the lpfnWndProc function that is assigned to it. The role of a window procedure is to process each relevant message that is sent to the window.

As one would expect, the default procedure DefWindowProc has standard responses for the most common messages: closes the window when the X button in the top-right is clicked (or when Alt+F4 is pressed), paints the window with the chosen background color (which we haven't selected yed).

The window procedure can be any function with the following signature:

C 
LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam);

It has four parameters:

  • hwnd – a handle to the window that received the message
  • uMsg – the numeric code for the message, such as WM_LBUTTONDOWN
  • wParam and lParam – additional information about the message. Their meaning depends on the message code

The function returns an LRESULT, which also has a different interpretation depending on the message code. UINT, WPARAM, LPARAM and LRESULT are all just 32-bit integers.

When you write your window procedure you can simply write code that only handles the messages you care about, and forward everything else to the default procedure.

C 
LRESULT CALLBACK WindowProc(HWND Window, UINT MessageKind,
							WPARAM wParam, LPARAM lParam) {
	LRESULT Result = 0;
	switch (MessageKind) {
		case WM_LBUTTONDOWN: {
			/* Process the mouse click */
		} break;

		/* Other cases */

		default: {
			Result = DefWindowProcW(Window, MessageKind, wParam, lParam);
		} break;
	}
	return Result;
}

int wWinMain(...) {
	/* ... */
	WindowClass.lpfnWndProc = WindowProc;
